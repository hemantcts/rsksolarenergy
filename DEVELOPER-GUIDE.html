1.What this website actually is

This is not a WordPress site. There is no admin dashboard, no database, and no plugins. Instead, the whole website is built from plain text files (mostly things that look like HTML) and turned into real HTML/CSS/JavaScript files by a tool called Astro before it goes online. This is called a "static site."

Why this matters to you

You cannot just open a page on the live website and edit it. You edit the source files on your computer, run one command to "build" the site, and then upload the result. Section 12 covers the upload step in detail.

Why built this way instead of WordPress: it is much faster to load, and there is no admin login or plugin system for someone to break into (the previous WordPress version of this site was compromised by a hacker who injected a spam link into the homepage — this rebuild deliberately has no equivalent attack surface).

2.One-time computer setup

Do this once on any computer you'll use to edit the site. If it's already set up, skip to Section 3.

Step 1 — Install Node.js

Node.js is the program that runs the website-building tool. Go to nodejs.org and download the LTS version (the button on the left, marked "Recommended for most users"). Run the installer and click through with the default options.

To check it installed correctly, open a terminal (see box below) and run:

node --version

You should see something like v22.x.x or higher. This project needs Node 22 or newer.

What's a "terminal"?

On Windows: press the Windows key, type PowerShell or Command Prompt, press Enter. On Mac: open Terminal from Applications → Utilities. It's a black or white window where you type commands instead of clicking things.

Step 2 — Get the project files

You should have a folder called rsksolarenergy containing this project (if you're reading this file, you probably already have it — it lives in that same folder). In your terminal, move into that folder: 

cd path\to\rsksolarenergy

(On this development machine that's currently cd C:\xampp\htdocs\rsksolarenergy.)

Step 3 — Install the project's dependencies

The project depends on a number of small tools and libraries (listed in package.json). This one command downloads all of them into a folder called node_modules: 

npm install

This takes a minute or two the first time. You only need to run it again if package.json changes.

Don't touch node_modules

It's a huge folder of other people's code, regenerated automatically. Never edit anything inside it, and never manually delete/copy it between computers — always run npm install fresh instead.

3.The commands you'll actually use

Run all of these from inside the project folder in your terminal.

See your changes live while you edit

npm run dev

This starts a "live preview" server. It will print a web address, usually http://localhost:4321 — open that in your browser. As you edit and save files, the page updates automatically. Leave this running in its own terminal window while you work; press Ctrl+C in that window to stop it.

Build the finished website

npm run build

This turns everything into the final, real website files, placed in a new folder called dist. This is the ONLY folder you upload to make the live site update (see Section 12). Always run this — and check it finishes with no red error text — before publishing anything.

Preview the exact built version

npm run preview

Unlike npm run dev (which is a live-editing preview), this serves the actual dist folder exactly as it will appear online. Use this as a final check after npm run build, before uploading.

Run the automated tests

npm test

This checks that the price/subsidy calculator's math still works correctly (88 checks). It should always say all passed in green. If anything is red, something broke a calculation — do not publish until it's fixed (or ask a developer).

Check for broken links and missing information

node scripts/launch-check.mjs

Run this after npm run build. It checks every internal link on the built site for typos/broken pages, and flags any business facts that are still placeholders. See Section 10 for reading its output.

5.The file types you'll see, in plain English

.astro files

Look almost exactly like an HTML file. There's a section at the very top between two --- lines (called "frontmatter") that pulls in data — you can usually leave that part alone. Below the second ---, it's ordinary HTML with regular class names, plus curly braces {likeThis} where a piece of text (a phone number, a price) gets inserted automatically. You can safely edit the plain text and HTML tags; be careful around anything in curly braces.

.mdx files

Used for blog posts and guides. It's Markdown (a simple way to write formatted text with plain symbols — ## Heading, **bold**, - bullet point) with a frontmatter block at the top like .astro files have, plus the occasional embedded component (a capitalised tag like <TariffTable />) that renders something more complex. Leave those component tags alone; write around them.

.json files

Structured data — the product catalogue is one of these. It's a list of items in { "key": "value" } pairs. The formatting (commas, quote marks, curly/square brackets) must stay exactly correct or the whole site will fail to build — copy an existing entry and edit its values rather than typing one from scratch.

.ts files

"TypeScript" — JavaScript with some extra structure. You'll mostly encounter these as data/config files (business.ts, solar-config.ts) where you're really just editing text and numbers inside a predictable shape. Change the values, not the surrounding structure.

6.How to: add a blog post

1

Go to src/content/blog/. Copy an existing .mdx file as a starting template (any one) and rename the copy — the filename becomes the page's web address, so use lowercase words separated by hyphens, e.g. solar-panel-cleaning-tips.mdx.

2

Edit the frontmatter block at the top (between the --- lines):

---
title: Your Post Title Here (Under 70 Characters)
description: 'A one-sentence summary, under 170 characters — shows in Google search results.'
published: '2026-09-12'
category: 'Panels and inverters'
tags: ['example tag', 'another tag']
faq:
  - q: A question a reader might ask?
    a: 'The answer, in a sentence or two.'
related:
  - href: /blog/some-other-post-slug/
    label: Text for the link to that other post
---

category must be exactly one of these (spelling matters):

  • Subsidy and bills
  • Sizing and systems
  • Hybrid, on-grid and off-grid
  • Solar pumps and agriculture
  • Panels and inverters
  • Installation and maintenance
  • Financing
  • Residential and commercial
  • ROI and payback

tags, faq and related are optional — delete them if you don't need them.

3

Below the second ---, write the post in Markdown. Headings use ##, paragraphs are just plain lines, bullet points start with -.

4

Run npm run dev and open the new post's address (e.g. http://localhost:4321/blog/solar-panel-cleaning-tips/) to check it looks right.

Never invent facts

Do not write specific prices, subsidy amounts, statistics or claims you haven't confirmed are true for RSK. This site's whole credibility rests on being more accurate than competitors — see Section 13.

7.How to: add or edit a product

All products live in one file: src/data/products.json. It's a list — find an existing product of the same type and copy its shape:

{
  "slug": "example-solar-panel-400-watt",
  "oldSlug": null,
  "title": "Example 400 Watt Solar Panel",
  "category": "solar-panels",
  "brand": "UTL Solar",
  "model": "UTL400-72M",
  "summary": "One or two honest sentences describing the product.",
  "description": ["A longer paragraph or two."],
  "features": ["A short bullet point", "Another bullet point"],
  "specs": {
    "columns": null,
    "rows": [
      { "label": "Maximum Power", "values": ["400W"] },
      { "label": "Warranty", "values": ["25 years"] }
    ]
  },
  "source": "utl-catalogue",
  "oldImage": "https://example.com/original-photo.jpg"
}

category must be one of: solar-systems, solar-panels, inverters, batteries, charge-controllers, ev-chargers, lighting-and-appliances.

Don't forget the comma after the previous product's closing } when adding a new one to the list — this is the single most common way to accidentally break the whole site's build. If the build fails right after editing this file, check for a missing or extra comma first.

Adding the product photo

Save the photo as a .webp file (convert it online if it's a .jpg/.png — there are many free "convert to webp" websites) into src/assets/products/, and name the file exactly the same as the product's "slug" value. For the example above, that's example-solar-panel-400-watt.webp. The site finds the photo automatically by matching the filename to the slug — no other file needs to reference it.

8.How to: change phone/address/prices/reviews

Open src/config/business.ts. It's a single structured list of facts, each with a short comment above explaining what it is. Find the value, change the text between the quote marks, save. For example:

phones: [
  { display: '+91 90419 96918', tel: '+919041996918' },
],

display is what visitors see; tel is the same number with no spaces/symbols (used to make the number tap-to-call). Keep both in sync if you change one.

Customer reviews live in a separate file: src/data/reviews.ts. Only add reviews that are genuinely real (copied from Google/Justdial) — never invent one.

9.How to: edit an existing page

Every page lives in src/pages/ as one .astro file, named after its web address (about.astro is /about/). Open the file, scroll past the frontmatter block (between the --- lines) into the HTML below, and edit text directly the way you'd edit any HTML file. Save, then check it in npm run dev.

A few pages have square brackets in their filename, like products/[slug].astro — do not rename or duplicate these. They're templates that automatically generate many pages at once (every product's page comes from that one file). Editing the template changes every product page it generates.

10.Before you publish anything

Every time, in this order, from the project folder:

npm run build
npm test
node scripts/launch-check.mjs
1

npm run build must finish with no red error text. If it errors, read the message — it usually names the exact file and line with a problem (very often a missing comma in a .json file, per Section 7).

2

npm test must say all checks passed.

3

node scripts/launch-check.mjs — read its output. A ✅ next to "Internal links" with "no broken internal links" means every link on the site points somewhere real. A 🟠 or 🔴 elsewhere lists business facts still marked as placeholders (see files/TODO-content.md for the full, current list) — these don't block publishing, they're just open items worth knowing about.

Only once all three are clean, move on to Section 12 to publish.

11.Google Analytics

The site reports visits to Google Analytics (measurement ID G-VJHJ211TLW). It's set up in one place: src/config/business.ts, the gaMeasurementId field.

  • To see the data: log into analytics.google.com with the Google account that owns this property.
  • To change the ID (e.g. a new GA property): edit the gaMeasurementId value in business.ts and rebuild.
  • To remove Analytics entirely: set gaMeasurementId: null in the same file. The tracking code disappears from every page automatically — no other file needs touching.
How it's wired in, for reference

The actual Google tag code lives in src/layouts/BaseLayout.astro (the file every single page is built from), and the site's Content Security Policy (a security setting) is configured in astro.config.mjs to specifically allow Google's analytics domains. If Analytics ever needs to be swapped for a different tool, both of those files are where to look.

12.Publishing the site live (Hostinger)

This site is a static site: publishing means building it, then uploading the finished files. There is no server-side install step, no database migration, nothing else to configure.

Step 1 — Build it

npm run build

This creates/updates the dist folder in your project. That folder — and only that folder's contents — is what gets uploaded.

Step 2 — Get your Hostinger file access

Log into hpanel.hostinger.com. You have two ways to upload; pick one:

  • File Manager (easiest, no extra software): in hPanel, go to Files → File Manager.
  • FTP (better for large/frequent updates): in hPanel, go to Files → FTP Accounts to see/create your FTP username, password and host address, then connect using a free FTP program like FileZilla.

Step 3 — Find the right folder

Open public_html (or, if this domain is set up as an "addon domain" alongside others on the same hosting account, the specific subfolder Hostinger created for it — check Websites in hPanel if unsure which folder maps to which domain).

If there's an old WordPress site here already

Back up anything you're unsure about first (Hostinger's File Manager has a "Compress" option to zip the existing folder before you touch it). This project intentionally replaces the old WordPress install — it was previously compromised by a hacker — so a clean folder is the goal, not a merge.

Step 4 — Upload

Upload everything inside your local dist folder into public_html — not the dist folder itself, its contents, so that index.html ends up directly inside public_html.

Turn on "show hidden files"

The dist folder includes a file called .htaccess that starts with a dot — most file managers and FTP clients hide files like this by default. It handles important redirects and security headers, so it must be uploaded too. In Hostinger's File Manager, use the Settings (gear icon) → Show Hidden Files option. In FileZilla, it's Server → Force showing hidden files.

Step 5 — Point the domain and check SSL

If the domain is already registered with Hostinger, this is usually automatic. If it's registered elsewhere, update its nameservers or DNS records to point at Hostinger (hPanel's Domains section shows the exact values to use). Hostinger issues a free SSL certificate automatically once DNS is pointing correctly — this can take anywhere from a few minutes to a few hours.

Step 6 — Test the live site

  • Open the real domain in a normal (not-logged-in) browser window and click through a few pages.
  • Try a URL without a trailing slash (e.g. /about) and confirm it redirects to /about/ — this confirms .htaccess uploaded correctly.
  • Check Google Analytics' Realtime report while browsing the live site to confirm visits are being recorded.

Publishing an update later

Repeat Steps 1 and 4 only: rebuild locally, then re-upload the changed files from dist (most FTP programs can "compare" folders and upload only what changed, which is much faster than re-uploading everything each time).

13.Rules this site was built to follow

This project was built against a detailed written specification. It's still in the project, in the files/ folder, and it's worth reading before making significant content changes:

FileWhat it covers
files/CLAUDE.mdThe overall brief — what this business needs the site to do, and hard rules (no e-commerce, WhatsApp-first, never invent facts)
files/DESIGN.mdVisual design rules — colours, type, tone of voice
files/MOTION.mdWhere animation is (and isn't) allowed on the site
files/SPEC-calculator.mdExactly how the price/subsidy calculator is supposed to behave
files/TODO-content.mdThe current, honest list of what's still unconfirmed or unfinished — check this before assuming a number is final

The two rules that matter most for day-to-day content work:

  • Never invent a fact. No made-up prices, statistics, certifications, customer names, or reviews. If a real number isn't available, say so or leave it out — don't guess and present it as confirmed.
  • No stock photography. Every photo should be a real photo of a real RSK product or installation, not a generic stock image.

14.Troubleshooting

"npm: command not found" / "'npm' is not recognized"

Node.js isn't installed, or your terminal needs restarting after installing it. Reinstall from nodejs.org, then close and reopen your terminal.

"npm run build" fails with a red error

Read the file path and line number in the error message — it points at the problem. The most common cause is a typo in src/data/products.json (a missing comma or quote mark). If you can't spot it, undo your last edit and try again to confirm that was the cause.

"Port 4321 is already in use"

You (or another terminal window) already have npm run dev running somewhere. Close that other terminal window, or just use the address it's already running at.

A product photo isn't showing up

The filename in src/assets/products/ must match the product's "slug" in products.json exactly, including hyphens, and must be a .webp file.

I uploaded the new site but the old one still shows

This is almost always a cached page in your own browser. Try a "hard refresh" (Ctrl+Shift+R on Windows, Cmd+Shift+R on Mac) or open the site in a private/incognito window. If it's genuinely not updating, check that you uploaded into the correct folder (Step 3, Section 12).

Still stuck

Copy the exact error message (or a screenshot) and the command you ran, and send it to a developer — that's almost always enough for someone familiar with the project to diagnose immediately.
